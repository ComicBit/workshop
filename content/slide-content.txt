======================================================================
01 — Give an old computer a new job
======================================================================
ON SCREEN
Turn an old computer into an always-on personal AI assistant.

Understand it. Set it up. Give it one useful task.
Warsaw · 28 October 2026

SPEAKER NOTES
Today is a small hands-on pilot, not a promise of a finished autonomous system.
We will connect the ideas to things you can actually inspect and use. The
computer must stay powered, connected and healthy to remain available.

OPENING QUESTION
What is one repetitive task you would like help with?

======================================================================
02 — What we are aiming to leave with
======================================================================
ON SCREEN
• A clear picture of how an agent works.
• A home server with separately managed services.
• Private access from your phone.
• One useful task completed by your own assistant.

SPEAKER NOTES
Demo 1 uses Hermes to set up bb and Paperclip. Demo 2 connects a separately
prepared personal interface to your own Hermes and starts onboarding.
The starter is in demos/02-hermes-webapp/; its default mode is local mock.
If live integration is unavailable, use Hermes directly and label the fallback.
Neither bb nor Paperclip is required for the personal assistant to run.

======================================================================
03 — A model is not the whole assistant
======================================================================
ON SCREEN
Model: generates answers and proposes next steps.
Harness: provides tools, context and an execution loop.
Connectors: give authorized access to other services.
Orchestration: coordinates work across agents and projects.

SPEAKER NOTES
The model does not gain access to a computer or inbox just by talking about it.
The surrounding software makes actions possible and controls access. Memory,
scheduling and tools are capabilities supplied by the chosen harness/setup;
their availability depends on configuration.
Use a simple example: drafting a reply is text generation; retrieving a real
message and saving a draft also require tools, access and verification.

======================================================================
04 — From answering to doing
======================================================================
ON SCREEN
Chat: “Here is how you could do it.”
Agent: “With your permission, I can try it and check the result.”

Inspect → Plan → Approve → Execute → Verify → Report

SPEAKER NOTES
An agent can take multiple steps using tools and respond to the results.
That does not make it infallible or entitled to act without limits. Approval
is especially important for destructive, privileged, costly or external actions.
For today's work, inspect the real machine before deciding what to change.

======================================================================
05 — A confident answer is not proof
======================================================================
ON SCREEN
Common failures
• Missing access or unclear instructions.
• Unintended changes or unexpected spending.
• Reporting success without testing it.

Ask: “What did you check, and what happened?”

SPEAKER NOTES
A running process does not prove an application can perform a real task.
A working page does not prove provider authentication works. Ask for observed
output, not a restatement of the plan. Report PASS, FAIL, PENDING or BLOCKED
with evidence and a next step. Never show an attempted install as a success.

======================================================================
06 — Local agent does not mean local model
======================================================================
ON SCREEN
Local agent + cloud model
Your machine runs the tools; a provider runs model inference.

Local agent + local model
Your machine runs both; compute and memory demands increase.

Check cost, data flow and hardware before choosing.

SPEAKER NOTES
The workshop can use a cloud model with an agent on an old computer.
Do not describe that setup as offline or entirely on-device. Model requests
may carry context outside the machine; speech recognition can also use vendor
servers. Review what each service receives. A chat subscription is not
necessarily API access, and API usage may be billed separately.

======================================================================
07 — Three tools, different jobs
======================================================================
ON SCREEN
Hermes
Personal agent: tools, memory, scheduling and assistant interactions.

bb
Agentic development workspace for technical project work.

Paperclip
Coordination of agents, projects, workflows and approvals.

SPEAKER NOTES
These are roles in our workshop, not claims that the products never overlap.
Hermes is our initial agent and the engine behind the later personal app.
bb and Paperclip are the services we ask it to install in Demo 1.
Provider authentication and integration support must be checked per tool.

======================================================================
08 — Why separate the responsibilities?
======================================================================
ON SCREEN
One host. Separate services. Clear ownership.

• Restart or update one service independently.
• See where data and configuration belong.
• Keep the personal assistant independent of the developer tools.

SPEAKER NOTES
Separate containers make management clearer; they do not remove the need for
permissions, authentication or backups. Reusing a provider does not mean
copying OAuth sessions between tools. Use supported authentication methods;
if an integration is unsupported, record the manual step instead of bypassing it.

TRANSITION
Now let's look at the machine that will host these services.

======================================================================
09 — Before we touch the disk
======================================================================
ON SCREEN
Installing Proxmox may erase the selected disk.

• Back up important files.
• Identify the correct target disk.
• Check virtualization, memory, storage and network access.
• Confirm before installing.

SPEAKER NOTES
Planning targets: spare x86-64 hardware, virtualization support, preferably
8+ GB RAM; 16 GB is more comfortable. These are not verified minimums for
all services together. Check each participant's machine and leave headroom.
If hardware is unsuitable, use the facilitator's prepared host for the demo.
The two-hour session starts with the baseline installation already complete.

======================================================================
10 — Proxmox: the host underneath the apps
======================================================================
ON SCREEN
Host: the physical machine running Proxmox.
Virtual machine: a guest with its own operating-system kernel.
LXC: a Linux container sharing the host kernel.

Today: one Proxmox host, three separate LXCs.

SPEAKER NOTES
Proxmox manages the guests and their resource allocations. Our proposed guests
are Hermes, bb and Paperclip. LXCs are not virtual machines and are not an
unbreakable security boundary. Prefer unprivileged containers; any additional
privileges need a documented reason and explicit approval.

======================================================================
11 — The system we are setting up
======================================================================
ON SCREEN
OLD COMPUTER / PROXMOX
├── Hermes LXC — agent, tools and memory
├── bb LXC — development workspace
└── Paperclip LXC — coordination

Phone/browser → private access → personal UI → Hermes

The personal UI does not depend on bb or Paperclip.

SPEAKER NOTES
The personal UI is a separate application prepared by the facilitator, not a
reskin of Hermes's dashboard. Its final deployment location remains to be
confirmed. The complete request path includes an authenticated app backend
between the browser and Hermes; we will show that in Demo 2.
Do not imply all containers become remotely reachable merely by installing
Tailscale on the host.

======================================================================
12 — Delegate a task, not unrestricted control
======================================================================
ON SCREEN
Before host changes, review:
• Which containers and resources will change?
• What access does the agent need?
• What could cost money or destroy data?
• How will we recover if it fails?

SPEAKER NOTES
The facilitator grants a limited, authorized Proxmox management route.
If the agent lacks access, it stops and explains what a human must configure.
Do not give it permanent unrestricted root just to make the demo easier.
Keep keys, private addresses, credentials and personal data out of this repo
and off shared presentation screens.

======================================================================
14 — First, inspect and propose
======================================================================
ON SCREEN
Hermes checks:
• Available CPU, RAM, storage and networking.
• Existing guests, free container IDs and permissions.
• Provider access and potential usage charges.

Review the resource plan before the first host change.

LIVE CHECK
Can we identify exactly which two new containers it proposes to create?
Is there enough capacity left for Proxmox and Hermes?

SPEAKER NOTES
Ask the agent to show allocations and impact in plain language. Do not assign
fixed resources on a slide: use the actual host inventory. If capacity is
insufficient, reduce scope with the human rather than silently overcommitting.

======================================================================
15 — Then, provision and install
======================================================================
ON SCREEN
After approval:
• Create two new unprivileged Debian LXCs.
• Install bb and Paperclip using current upstream instructions.
• Configure persistent data, logs and supervised services.
• Keep access private and authenticated.

LIVE CHECK
Inspect actual container IDs, service state and installation logs.

SPEAKER NOTES
Do not modify unrelated guests or replace the original Hermes LXC.
Authentication may need a user-performed login. Use supported methods and
report any missing access. An interactive installer left running is not a
restart-safe service. Extra container privileges require a separate decision.

======================================================================
16 — Test a task, not just a page
======================================================================
ON SCREEN
For both services:
• Open the UI.
• Run a real agent-backed task.
• Inspect the result and logs.
• Verify restart behavior and persistent state.

PASS / FAIL / PENDING / BLOCKED — with evidence.

SPEAKER NOTES
Suggested small bb test: create a README in a disposable workspace and inspect
the actual file. For Paperclip, use a supported authenticated adapter to run a
small task and inspect its result. These are proposed tests, not prevalidated
integrations. An unauthenticated adapter is BLOCKED, not a successful task.
Use demos/acceptance-tests.txt as the full checklist. If time runs out, keep
incomplete checks visible and continue with the working Hermes baseline.

======================================================================
17 — Make tomorrow's restart boring
======================================================================
ON SCREEN
Restart: guest starts, service restarts, data remains.
Update: record version → back up → update → test.
Recovery: know how to restore the previous working state.

An update command is not a recovery plan.

SPEAKER NOTES
Separate OS security updates from application upgrades. Prefer approval for
breaking changes and major versions. Use supported update instructions; do
not run unrestricted “latest” installs under root. Keep backups outside the
service being updated where possible. Distinguish configured policy from a
restore that has actually been tested.

TRANSITION
The server works here. Next, can you reach it when you leave?

======================================================================
18 — Tailscale: a private route home
======================================================================
ON SCREEN
Your phone and home server can connect over a private network.

• Enroll authorized devices in your own tailnet.
• Choose a private path to each service.
• Keep application login enabled.

No public router port forwarding for this workshop.

SPEAKER NOTES
Follow guides/tailscale.txt and current official Proxmox instructions.
Installing Tailscale on the host can provide a path to Proxmox, but LXCs need
an intentional access route: private reverse proxy, appropriate guest enrollment
or controlled routing. Do not enable Funnel or broad public exposure.
A private network does not replace application authentication or backups.

======================================================================
19 — The phone test
======================================================================
ON SCREEN
1. Connect the phone to your own tailnet.
2. Turn Wi-Fi off.
3. Open the private service URL over cellular.
4. Sign in and verify access.

If it fails, diagnose the private route. Do not open router ports.

LIVE CHECK
Prove the connection is remote, private and usable from the phone.

SPEAKER NOTES
Check the intended service, not just the Tailscale device list. Verify network
rules and application login. Resolve unexpected certificate/identity warnings
rather than teaching people to ignore them. Keep private URLs in local notes.

======================================================================
22 — Keep the key out of the browser
======================================================================
ON SCREEN
Browser / personal UI
        ↓ authenticated session
App backend / proxy
        ↓ server-held credential
Your Hermes API
        ↓ approved tools
Your tasks and services

bb and Paperclip are not in this request path.

SPEAKER NOTES
The backend holds API_SERVER_KEY; never put it in frontend code or browser
storage. Use only documented routes supported by the installed Hermes version
and verify real responses. Restrict the actions the app can request; do not
create an arbitrary shell-execution endpoint. Private networking complements,
not replaces, app authentication and authorization.

======================================================================
23 — Start with a short conversation
======================================================================
ON SCREEN
Speak or type. One question at a time.

“What is taking most of your attention right now?”
“What repetitive task would you like help with?”
“What boundaries should I respect?”

Review the proposed profile before saving it.

SPEAKER NOTES
Use prompts/03-personal-onboarding.md for behavior. Begin onboarding inside
the custom UI when it is available. The microphone transcribes speech to text;
this is not a text-to-speech demo. Activate recording only with consent and
explain if the recognition service may process audio in the cloud. Typing is
always the fallback. Ask only for useful voluntary information.

======================================================================
24 — Memory you can inspect and change
======================================================================
ON SCREEN
Before remembering anything:
• Show the proposed facts and preferences.
• Let the person accept, edit or decline.
• Provide a way to edit or delete saved context later.

Your answers are facts. The assistant's guesses are not.

LIVE CHECK
Approve a small profile, reload the app, and verify it persists privately.

SPEAKER NOTES
A summary shown once in chat is not proof of persisted memory. Show the actual
editable profile where supported. Store neither secrets nor unnecessary
sensitive information. If using the Hermes fallback, demonstrate only supported
memory behavior and mark custom profile UI checks pending.

======================================================================
25 — Gmail is optional, not a shortcut to consent
======================================================================
ON SCREEN
Connect only if available and wanted.

Authorize the account → verify connection → approve a bounded read.

Sending, deleting or changing messages needs separate review.
No Gmail? Continue with the context you chose to share.

SPEAKER NOTES
This is an optional extension after the core path works, not a baseline
requirement. Verify Nous Portal/connector eligibility and the actual supported
authorization route. Do not ask for a Google password in chat or build a new
OAuth client by default. A button press alone does not mean “connected”.
If authorized, agree a small date/message limit and summarize only retrieved
evidence. Do not display private email content on shared screens.
In the two-hour session, use this slide to explain boundaries and skip setup.

======================================================================
26 — Suggest something useful, with a reason
======================================================================
ON SCREEN
Example — only if you told the assistant this:
“I spend too much time preparing for weekly meetings.”

Suggestion: create a reusable meeting-preparation checklist.
Why: it addresses a task you said you repeat.
Access needed: your answers; no inbox connection.

Review, adjust or decline.

SPEAKER NOTES
This is an illustrative exchange, not a claim about either participant.
Generate up to three suggestions from actual onboarding answers. Explain the
basis and permissions for each. Do not invent deadlines, inbox contents or
financial interests. Select one small task with an inspectable output rather
than adding more integrations or scheduling a broad recurring automation.

======================================================================
27 — Approve one task. Inspect the result.
======================================================================
ON SCREEN
1. Agree on the exact action.
2. Approve the required access or changes.
3. Let Hermes execute through available tools.
4. Open the actual output.
5. Record what succeeded or what blocked it.

A promise is not a completed task.

LIVE CHECK
Complete a low-risk task and show its traceable result in activity/history
where supported. For example: save an approved checklist and read it back.

SPEAKER NOTES
Use a supported private persistence tool; do not invent an API or pretend a
file exists because the assistant printed its name. A text-only answer can
be useful, but is not proof of a tool action. Verify tool output or retrieve
the saved artifact. If access is missing, show the blocker and a safe manual
workaround. For the custom UI, also verify phone access and restart behavior.
Use the Demo 2 acceptance checklist; leave incomplete features marked pending.

======================================================================
28 — What actually worked today?
======================================================================
ON SCREEN
Review the evidence:
• bb and Paperclip: installed, tested, restart-safe?
• Phone: private access over cellular?
• Assistant: reviewed profile and one verified task?
• Custom UI and Gmail: working, pending or blocked?

Name the next step for anything unfinished.

SPEAKER NOTES
Use demos/acceptance-tests.txt, not memory or enthusiasm. Read the actual
status of each path. A native Hermes fallback is useful, but is not a completed
custom UI integration. Configuring a backup is not the same as testing restore.
Do not mark untouched checks PASS. Keep credential details and addresses private.

29 — Give it one job tomorrow
======================================================================
ON SCREEN
Choose one small, personally useful task.

Keep access narrow.
Review the result.
Maintain backups and a recovery path.
Expand only when you trust the evidence.

before enabling it. Know how to restart services, check logs and revoke access.
Do not leave temporary elevated setup permissions in place after the workshop.
